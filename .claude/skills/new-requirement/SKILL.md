# New requirement

Write the requirement for: `$ARGUMENTS` (if empty, use what was just agreed in the conversation).

Current requirements:

!`ls -1 requirements/ 2>/dev/null | grep -E '^[0-9]{4}-' || echo "(none yet)"`

## Steps

1. **Check there is enough agreement.** If scope, the affected projects or the
   acceptance criteria are unclear, ask the user in Spanish before writing. Do not
   invent business rules; if something is undecided, list it under *Open questions*.
   **Read the related epics** in `epics/`: if the requirement is part of
   one, set `epic: EXX`, respect what the epic already decided, and add the requirement
   to the epic's `requirements` list.
2. **Read the ADRs it touches** (`docs/adr/README.md` index). A requirement never
   contradicts an accepted ADR; if it needs to, stop and propose a new ADR first
   (skill `new-adr`).
3. **Number and name.** Next number = highest `NNNN` above + 1, four digits. Slug in
   English kebab-case, short: `0003-match-list.md`.
4. **Write the file** from `requirements/_template.md`, in **English**, with
   `status: pending`, today's date in `created`, and `projects` with the names of
   `workflow.json`. Diagrams only in Mermaid, never ASCII art.
5. **Do not touch code.** This skill only writes the document.
6. **Reply in Spanish** with a short summary (goal, scope, criteria count, open
   questions) and ask the user to review it. Implementation starts only when the user
   approves it.

## Quality bar for a requirement

- Goal in one or two sentences: the *why*, from the user's point of view.
- Scope lists what is in **and what is out**.
- Acceptance criteria are verifiable (each one becomes at least one test), numbered
  `AC-1`, `AC-2`...
- Data model changes list tables and columns in English (they become an autogenerated
  migration).
- API changes list method, path, auth, request and response shape.
- Screens list their states: loading, empty, error, data, and what is "Próximamente".
- When one module's event changes another module's state, say where the rule lives
  ("Where the rule lives"): one public function in the owning module, called from one
  place.
- Write what is used; discarded options are named only by kind in *Open questions* or
  the ADR, never "no X for now".
